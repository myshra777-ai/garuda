# MCP Sessions and Tool-Call Tracking

**Status:** Implemented baseline in the current v1.5.0 tree; retained design details document the schema and operational contract.
**Scope:** MCP session lifecycle, tool-call records, retention/job state, and the observability data consumed by the owner-facing Control Plane.
**Implementation anchors:** `cmd/garuda-mcp/session_tracking.go`, `migrations/088_mcp_sessions.sql`, `migrations/089_control_plane_readonly_role.sql`, and `internal/api/control_plane_operations.go`.
**Related:** [Control Plane design and implementation notes](control-plane.md), [metric definitions](control-plane-metrics.md), [Garuda specifications](../SPECS.md).

---

## Non-goals

This spec does not implement analytics, per-user tracking, session replay,
or cross-client correlation. It records what happened. It does not draw
conclusions from what happened. Behavioral analysis, if it ever exists,
is a separate product with a separate privacy review.

---

## Purpose

The current MCP server has a best-effort session and tool-call write path.
It records session start, tool-call status/duration and session closure for
the owner-facing Control Plane. Session creation or call-record failures are
logged and do not block the MCP handshake/tool response; when session creation
fails, tool events can be recorded against the seeded orphaned-session sentinel.
This preserves agent availability but means a database outage can reduce
session-level attribution.

The purpose is observability, not analytics. We record what happened so
that an operator can see it. We do not derive behavioral profiles, track
individual users, or correlate sessions with people.

## Schema

### `mcp_sessions`

```sql
CREATE TABLE mcp_sessions (
  id                UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  tenant_id         UUID NOT NULL,
  workspace_id      UUID,
  session_token     TEXT NOT NULL,
  client_name       TEXT NOT NULL,
  client_version    TEXT,
  agent_id          TEXT,
  started_at        TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  last_activity_at  TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  closed_at         TIMESTAMPTZ,
  close_reason      TEXT,
  request_count     INT NOT NULL DEFAULT 0,
  tool_call_count   INT NOT NULL DEFAULT 0
);

CREATE INDEX mcp_sessions_tenant_active_idx
  ON mcp_sessions (tenant_id, last_activity_at DESC)
  WHERE closed_at IS NULL;

CREATE INDEX mcp_sessions_started_idx
  ON mcp_sessions (started_at DESC);

CREATE INDEX mcp_sessions_stale_idx
  ON mcp_sessions (last_activity_at)
  WHERE closed_at IS NULL;
Why session_token and not session_id. The original draft had a
session_id TEXT NOT NULL column, but the write path said "store the
returned UUID in the MCPServer struct," which is ambiguous. The column is
renamed session_token and its role is explicit: it is the stable
identifier the MCP server process generates at startup and includes in
every log line. The id column is the database's own UUID. The two are
correlated but serve different purposes — id for foreign keys,
session_token for log correlation and client-facing reporting.

The value is generated by uuid.New().String() in the MCP server's
startup path — the same UUID that MCPServer.sessionID already holds for
log correlation. It is not a security primitive. It is not used for
authentication. It is a stable identifier that appears in every log line
from one process run, so that an operator reading logs can correlate
"these 47 calls came from the same client process." Any future use of
session_token for authentication would be a security defect — the
column is indexed for lookup, not validated for access.

Why close_reason. A session can close for four reasons: graceful
shutdown ("graceful"), stale timeout ("stale"), crash detected by the
stale job ("crashed"), or reactivation overwrite ("reactivated"). A
fifth sentinel value "orphaned" marks the synthetic session that
receives tool calls whose parent session write failed — see §Sentinel
session below. Recording the reason makes the Operations tab able to
distinguish "healthy session ended" from "session died mid-flight."

Why three indexes. The active index serves "online now" and per-tenant
active-session queries. The started index serves retention-curve queries.
The stale index serves the nightly stale-session job — without it, that
job is a full table scan.

mcp_tool_calls
```sql
CREATE TABLE mcp_tool_calls (
  id             UUID PRIMARY KEY DEFAULT gen_random_uuid(),
  session_id     UUID NOT NULL REFERENCES mcp_sessions(id) ON DELETE CASCADE,
  tool_name      TEXT NOT NULL,
  duration_ms    INT NOT NULL,
  status         TEXT NOT NULL CHECK (status IN ('ok', 'error')),
  error_message  TEXT,
  called_at      TIMESTAMPTZ NOT NULL DEFAULT NOW(),
  args_summary   JSONB
);

CREATE INDEX mcp_tool_calls_session_idx
  ON mcp_tool_calls (session_id, called_at DESC);

CREATE INDEX mcp_tool_calls_tool_idx
  ON mcp_tool_calls (tool_name, called_at DESC);

CREATE INDEX mcp_tool_calls_recent_idx
  ON mcp_tool_calls (called_at DESC)
  WHERE status = 'error';
```
Why the check constraint on status. Two values are valid. Anything
else is a bug in the write path. The constraint catches it at the database
rather than three months later when a metric reads a status it doesn't
recognize.

Why the partial index on errors. The Operations tab queries "errors in
the last hour" on every page load. The partial index keeps that query
cheap even as mcp_tool_calls grows.

job_state
```sql
CREATE TABLE job_state (
  job_name         TEXT PRIMARY KEY,
  last_run_at      TIMESTAMPTZ NOT NULL,
  last_run_status  TEXT NOT NULL CHECK (last_run_status IN ('ok', 'error')),
  last_error       TEXT
);
```
Two jobs use it:

Job name	Purpose	Cadence
mcp_sessions.prune	Delete old sessions and tool calls	hourly
mcp_sessions.mark_stale	Close sessions with no recent activity	every 5 minutes
Each job, on wake, reads last_run_at for its own row and skips if the
elapsed time is below the cadence. On completion, it upserts the row with
the current timestamp and status. A failure records
last_run_status = 'error' and the error string in last_error, then
continues — a failed run does not block the next.

The table is created by the same migration that creates mcp_sessions.
It is not a general-purpose scheduler; it exists so that two specific jobs
in this spec have a durable place to record when they last ran.

Sentinel session
```sql
INSERT INTO mcp_sessions (
  id, tenant_id, session_token, client_name, agent_id,
  started_at, last_activity_at, close_reason
) VALUES (
  '00000000-0000-0000-0000-000000000000',
  '00000000-0000-0000-0000-000000000001',
  'orphaned-session',
  'orphaned',
  'orphaned',
  NOW(), NOW(), 'orphaned'
) ON CONFLICT (id) DO NOTHING;
```
Why a sentinel session exists. If the session-row insert fails at
startup — the database is briefly unreachable, or the insert conflicts —
the MCP server logs a warning and continues. Without a sentinel, the next
tools/call would fail its foreign key reference to mcp_sessions(id).
The choice would be to either drop the tool call (losing the observability
that matters most — sessions where something went wrong at startup) or to
retry the session insert on every call (a hot path with a slow branch).

The sentinel row is the third option. Tool calls from orphaned sessions
are recorded against the sentinel and remain visible in the Operations
tab if you look for them. Every Operations query adds a
WHERE client_name != 'orphaned' guard, so the sentinel does not pollute
normal counts.

Write path
The MCP server (cmd/garuda-mcp/main.go) writes on four events.

On initialize handshake
Insert a row into mcp_sessions. Extract:

Field	Source	Fallback
client_name	params.clientInfo.name	"unknown-client"
client_version	params.clientInfo.version	NULL
agent_id	Request args, then GARUDA_AGENT env	"mcp-agent"
tenant_id	Resolved via resolveTenant(args)	Canonical tenant
workspace_id	Resolved via GARUDA_WORKSPACE env	NULL
session_token	uuid.New().String() at process start	—
Store the returned id in the MCPServer struct for the process lifetime.
If the insert fails, log at WARN and continue — session tracking is
best-effort and must never block tool execution. Subsequent tool calls
for that session are recorded against the sentinel session row.

On every tools/call
In a single transaction:

Insert a row into mcp_tool_calls with tool_name, duration_ms,
status ("ok" or "error"), error_message (from the handler's
error if present), and args_summary (whitelisted args only — see
below).

Update the parent session:

```sql
UPDATE mcp_sessions
   SET last_activity_at = NOW(),
       request_count = request_count + 1,
       tool_call_count = tool_call_count + CASE WHEN $2 = 'ok' THEN 1 ELSE 0 END
 WHERE id = $1;
```
Why request_count increments on both ok and error, but tool_call_count
only on ok. A failing tool call is a request that reached the server,
but it is not a successful execution. The distinction is what lets the
Operations tab compute a per-tool error rate, not just an error count.

Reactivation race. If the stale-session job has already marked this
session closed_at IS NOT NULL and a new tool call arrives — possible if
the client slept for 30+ minutes without sending a shutdown signal — the
update must clear closed_at and set close_reason = 'reactivated':

```sql
UPDATE mcp_sessions
   SET last_activity_at = NOW(),
       closed_at = NULL,
       close_reason = 'reactivated',
       request_count = request_count + 1,
       tool_call_count = tool_call_count + CASE WHEN $2 = 'ok' THEN 1 ELSE 0 END
 WHERE id = $1;
```
Without this, a sleeping client's later calls would silently fail to update
anything, and the session would appear frozen in the stale list.

On graceful shutdown
```sql
UPDATE mcp_sessions
   SET closed_at = NOW(), close_reason = 'graceful'
 WHERE id = $1;
```
The shutdown handler must run before os.Exit(0) — the current main()
installs a signal handler that calls os.Exit(0) directly. That handler
needs to be extended to perform the close-write first, with a short
timeout, then exit.

On crash
The stale-session job marks sessions whose
last_activity_at < NOW() - INTERVAL '30 minutes' and closed_at IS NULL
as closed:

```sql
UPDATE mcp_sessions
   SET closed_at = NOW(), close_reason = 'stale'
 WHERE closed_at IS NULL
   AND last_activity_at < NOW() - INTERVAL '30 minutes'
   AND client_name != 'orphaned';
```
Why the stale threshold is 30 minutes. A session is stale if it has
not called a tool in 30 minutes. This is not the same as "the process is
dead" — a client that is thinking, waiting on user input, or running a
long external operation is not making tool calls either. The 30-minute
window is a heuristic, not a fact. When the job closes a session, it uses
close_reason = 'stale' to signal that the closure was inferred, not
observed.

Enforcement. The tool list is extracted into a package-level
variable in cmd/garuda-mcp/tools.go:

go
var allTools []ToolDefinition

type ToolDefinition struct {
    Name        string
    Description string
    InputSchema map[string]any
    Whitelist   []string // args permitted in args_summary
}
Both handleToolsList and the whitelist test iterate allTools. The
test asserts that every ToolDefinition has a non-empty Whitelist
field if the tool accepts args, and that handleToolsList returns exactly
len(allTools) entries. Adding a tool means editing one variable.

Why the list lives in a variable and not in the handler. Parsing
handleToolsList's output to discover the tool list inverts the
dependency — the test would depend on the handler's JSON encoding, and
any refactor of that function breaks the test even when the tools haven't
changed. One source of truth for the list, one place to edit.

Why this is a whitelist and not a blacklist. The two options are
"record everything unless it looks sensitive" and "record nothing unless
it is known safe." The first fails open — a new argument is recorded by
default until someone notices. The second fails closed — a new argument
is dropped by default until someone adds it. For an observability table
that operators read, failing closed is the correct default. The cost is
that adding a tool requires one extra field. That is the right tax.

Sampling and volume
No sampling. Every tool call is recorded. The 30-day retention cap is
the backpressure mechanism.

At the observed rate — tens of calls per session, tens of sessions per day
in the beta phase — mcp_tool_calls grows by a few hundred rows per day.
Even at 100x that rate, 30 days of history is under 10 million rows, well
within PostgreSQL's comfortable range for the indexes defined.

If volume ever becomes a problem, the correct response is to shorten
retention, not to add sampling. Sampled data cannot answer "how many times
did this tool fail?" — it can only answer "what fraction of the sample
failed." The former is the question the Operations tab asks.

Retention and pruning
Table	Retention	Rationale
mcp_sessions	90 days	Long enough for a quarterly retention curve
mcp_tool_calls	30 days	High volume; 30 days covers debugging needs
The pruning job runs as a goroutine in the API server, checked once per
hour against a last_run_at timestamp in job_state. It is not a
separate process and does not require an external scheduler.

On each run:

```sql
DELETE FROM mcp_tool_calls
 WHERE called_at < NOW() - INTERVAL '30 days';

DELETE FROM mcp_sessions
 WHERE closed_at IS NOT NULL
   AND closed_at < NOW() - INTERVAL '90 days'
   AND client_name != 'orphaned';
```
Cascading delete on mcp_tool_calls.session_id means deleting a session
removes its calls. The order matters: delete old tool calls first, then
old sessions. Reversing the order would orphan tool calls whose parent
session has been deleted, briefly, until the next pruning pass —
harmless with ON DELETE CASCADE, but the correct order is cheaper.

The sentinel session is excluded from both deletes. It is the permanent
parent of orphaned tool calls and must not be pruned.

The pruning job must never delete an open session. The
closed_at IS NOT NULL guard ensures this. An active session is safe
regardless of its started_at.

Query patterns
Five queries the rest of the system depends on, with their index needs
documented.

Query	SQL	Index
Online now	SELECT COUNT(*) FROM mcp_sessions WHERE last_activity_at > NOW() - INTERVAL '5 minutes' AND closed_at IS NULL AND client_name != 'orphaned'	mcp_sessions_tenant_active_idx (partial)
Recent sessions (24h)	SELECT * FROM mcp_sessions WHERE started_at > NOW() - INTERVAL '24 hours' AND client_name != 'orphaned' ORDER BY started_at DESC	mcp_sessions_started_idx
Client breakdown	SELECT client_name, COUNT(*) FROM mcp_sessions WHERE client_name != 'orphaned' GROUP BY client_name	sequential scan; acceptable at current volume
Tool errors (1h)	SELECT tool_name, COUNT(*), COUNT(*) FILTER (WHERE status = 'error') FROM mcp_tool_calls WHERE called_at > NOW() - INTERVAL '1 hour' GROUP BY tool_name	mcp_tool_calls_recent_idx for the error leg
Stalled sessions	SELECT * FROM mcp_sessions WHERE closed_at IS NULL AND last_activity_at < NOW() - INTERVAL '30 minutes' AND client_name != 'orphaned'	mcp_sessions_stale_idx
The client-breakdown query has no index because it runs once per page load
on the Operations tab and the row count is low. Adding an index would slow
writes for a read that costs milliseconds.

Privacy
args_summary never contains free-form text. The whitelist is the
enforcement.

error_message is the model-visible error string. It may contain file
paths from the tenant's workspace. Never shown outside the Control
Plane. The tenant-facing Agents tab shows the tool name and duration
but not the error message.

error_message stores the raw error string including any file paths the
failure produced. It is visible in the Control Plane's Operations tab.
It is never visible to the tenant. This is intentional: the owner needs
raw errors to debug, and the tenant gains nothing from seeing the same
text scoped to their own failures.

Session identifiers are opaque to the tenant. A tenant sees "3 sessions
in the last 24h" but not the session tokens themselves.

No correlation with a human user. An MCP session is a client process,
not a person. The Control Plane reports sessions, never users.

Open questions
Does workspace_id remain NULL when the client has not set
GARUDA_WORKSPACE? Current answer: yes. A session that has not yet
resolved a workspace has no workspace to record. The first tool call
that resolves a workspace does not backfill the session — the session's
workspace_id stays NULL for its lifetime. If backfilling is wanted,
it must be explicit in the write path.

Should client_version be normalized? Cursor sends "0.42.3",
Claude sends "1.2.0", and some clients send nothing. The column
accepts any string. If the Control Plane wants a "clients by version"
chart, it needs a normalization rule. Not defined here.

What happens when DATABASE_URL is unreachable at session creation?
Current answer: the write fails, the session is orphaned, and its tool
calls are recorded against the sentinel session. This is the correct
failure mode — observability must never block execution — but it means
a database outage produces a gap in the per-session record. If
per-session attribution during an outage matters, the write path needs
a local buffer and a retry loop. Not defined here.

## Current implementation and verification boundaries

The original Definition of Done below was the design acceptance checklist for
the implementation. It is retained in Git history rather than presented as a
current test report. The current repository's reference MCP/Talon verifier is
documented as 30/30 checks in [EVIDENCE.md](../../EVIDENCE.md); that verifier
covers protocol and integration behavior, not every persistence lifecycle,
retention schedule, or outage scenario listed in this historical checklist.

Implementation entry points:

- `recordSessionStart`, `recordToolCall`, and `closeSession` in
  `cmd/garuda-mcp/session_tracking.go`.
- Tables, indexes and the orphaned-session sentinel in
  `migrations/088_mcp_sessions.sql`.
- The read-only Control Plane database role in
  `migrations/089_control_plane_readonly_role.sql`.
- Session and tool-call views in
  `internal/api/control_plane.go` and
  `internal/api/control_plane_operations.go`.

**Operational boundary:** tracking writes are best effort. They must not
block MCP operation, but an unavailable database can leave a session row
missing and route subsequent tool-call records through the sentinel.
